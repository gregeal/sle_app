Verdict: the happy paths pass, but the foundations need corrections before the

## Findings

### R1 — P1 — Placement does not protect microphone lifecycle

Location: `sle_prep/lib/features/weekly/placement_screen.dart:46`.

The screen starts its shared speech service without observing app lifecycle or
registering with `wordHelpGuardProvider`. It stops on disposal, manual stop, or
submission, but not when the app is backgrounded or another route covers it.
A fake-service widget probe confirmed `isListening=true`, no stop call after
backgrounding, and `guard.blocked=false` during capture. Actual background audio
behavior depends on the platform; the app itself does not request a stop.

Fix: reuse the existing VoiceDraft lifecycle/guard behavior, serialize start/stop,
surface initialization/listening failures, and stop capture on backgrounding and
navigation. Verify pause, covered route, disposal during startup, and retry.

### R2 — P1 — Assignment evidence is not trustworthy or resolvable

Locations: `sle_prep/lib/features/weekly/weekly_class_screen.dart:97`,
`sle_prep/lib/data/db/weekly_daos.dart:117`.

The class marks both teaching and speaking as `courseLesson`, with the study-week
ID as `evidenceId`. Realtime actually saves an `OralAttempt` with mode `class`,
but its ID is not returned to the class, and `oralAttempt` is not an accepted
weekly evidence kind. A callback probe confirmed speaking evidence was
`courseLesson/1` for week 1. The future review cannot resolve that reference into
the speaking transcript/feedback. Quiz answers and score are also not saved as
weekly evidence.

The DAO compounds this by accepting any positive evidence ID, including missing
records or a reading attempt for speaking. The earlier adversarial probe confirmed
that nonexistent, mismatched evidence completes an assignment.

Fix: return the saved attempt ID from the assessment path; add typed evidence
references and validate record existence, skill, week/lesson association, and
completion. Define explicit self-reported evidence for solo/offline tasks and a
durable teaching/quiz record. First-completion-wins must not freeze bogus evidence.

### R3 — P2 — Class steps are neither gated nor resumable

Locations: `sle_prep/lib/features/weekly/weekly_class_screen.dart:30`, `:139`, `:160`.

Every step header and Continue button advances unconditionally. A learner can
reach homework without checking comprehension. All step/answer/check/practice
state lives in the widget; reopening starts at step zero and forgets answers.
The probe reached practice without a quiz, then confirmed reopening reset to zero.
This conflicts with the plan's ordered, resumable class contract. Formative wrong
answers should permit progress, while an unattempted check is a separate state.

Fix: persist stage, answers, formative result and practice outcome by week;
restore them on entry. Require the intended preceding activity or an explicit,
recorded skip. Save successfully before showing an activity as completed, with
retry if persistence fails.

### R4 — P2 — Guided practice has no promised fallback and depends on grading

Locations: `sle_prep/lib/features/weekly/weekly_class_screen.dart:104`, `:331`;
`sle_prep/lib/features/coach/realtime_interview_screen.dart:415`;
`sle_prep/lib/domain/llm/oral_coach.dart:294`.

The only practice route is Realtime. Offline instructions say to skip and return
later; no manual-turn/device-STT or solo path is offered. Practice is considered
done only after a separate AI assessment succeeds. This loses completion when
speaking succeeded but assessment fails. The existing assessor also rejects more
than 20 exchanges; a short-turn teacher conversation can exceed that limit, leaving
the same transcript unable to pass assessment retries.

Fix: provide the agreed fallback; save practice evidence before optional feedback,
track assessment pending/failed separately, and handle long sessions by bounded
assessment chunks or another explicit policy. Return an evidence record even when
feedback is pending. Use class-specific introduction and feedback language: the
shared screen still advertises an examiner and progression toward C to A-to-B users.

### R5 — P2 — Plan validation admits unusable weeks

Locations: `sle_prep/lib/domain/weekly/weekly_plan.dart:186`;
`sle_prep/lib/data/db/weekly_daos.dart:41`.

An empty assignment list parses as a valid plan. Aggregate validation does not
enforce unique spec IDs, configured day bounds, daily/weekly budgets, skill shares,
payload consistency, or the track/lesson catalog binding. The earlier probe stored
a nonexistent lesson successfully. `WeeklyClassScreen` then uses an unguarded
`findCourseLesson`, so such a week fails when opened.

Fix: one shared validator for composed, restored and persisted plans, including
catalog bindings and allowed payload modes. Add database constraints for stable
assignment identity where appropriate. Invalid stored data needs a recovery UI.

### R6 — P2 — Supported schedules can violate vocabulary allocation

Location: `sle_prep/lib/domain/weekly/weekly_plan.dart:333`.

For 3 study days at 30 minutes, the allocation is teaching 5, speaking 40,
listening 15, reading 15, writing 15, vocabulary 0. The published vocabulary floor
is 5%. The allocator deliberately gives vocabulary away to satisfy other floors;
the existing contract tests do not assert vocabulary or teaching share limits.

Fix: reject schedules infeasible with five-minute blocks, use finer rounding, or
publish an explicit reduced-budget contract. Test every published bound across
all accepted day/minute combinations, including four study days and extremes of
adaptation. The default 5-by-60 plan passes the current checks.

### R7 — P2 — Placement can be unreliable or impossible to complete

Locations: `sle_prep/lib/domain/weekly/placement.dart:195`;
`sle_prep/lib/features/weekly/placement_screen.dart:172`.

Placement accepts 40 characters of spoken transcript and an empty written sample.
It cannot establish reading/listening or pronunciation/fluency from those inputs.
The UI offers no editable spoken transcript or typed fallback: microphone denial,
unsupported recognition, or a transcription mistake can block or distort placement.
It also bypasses the existing choice of higher-quality cloud dictation.

Fix: reuse VoiceDraft with editable transcription, meaningful evidence requirements,
explicit provisional/insufficient-evidence outcomes, and a recoverable/manual track
choice. Keep per-skill unknown states so absent evidence cannot later satisfy a
progression gate. Validate stored placement version and track/level consistency.

### R8 — P2 — Closure does not freeze the evidence behind the report

Locations: `sle_prep/lib/data/db/weekly_daos.dart:117`, `:154`, `:165`.

Closed weeks accept later assignment completions, changing historical totals after
the report was saved. `closeStudyWeek` accepts arbitrary report text; the earlier
probe stored `not json`. Aggregation sums planned block minutes when checked off,
not measured practice time, so it cannot answer actual time-spent questions.

Fix: validate a typed report before persistence and record its evidence snapshot or
revision. Either prohibit post-closure changes or regenerate/version affected
reports. Separate planned, credited and measured minutes in storage and wording.
Report generation itself belongs to P5-6; these DAO contracts need to support it.

### R9 — P2 — Lesson progression treats scheduling as learning

Location: `sle_prep/lib/features/weekly/weekly_home_screen.dart:72`.

`startNextWeek` treats every lesson in weekly history as taught, regardless of
class/assignment completion. It ignores existing self-paced course evidence and,
when all 16 lessons appear in history, silently chooses the last lesson forever.
This is incompatible with evidence-based advancement and a defined track finish.

Fix: explicitly distinguish scheduled, taught and mastered lessons. Define how
historical course work affects entry, how incomplete weeks affect repetition, and
what happens at track completion. P5-6 can implement full mastery gates, but the
current helper should not silently fabricate a taught state or repeat indefinitely.

## Additional hardening and plan decisions

- The Realtime teacher override uses `session.update`, which the official API
  supports. However, `_configureAndOpen` immediately sends `response.create`, and
  the parser discards the effective configuration from `session.updated`. Confirm
  the requested persona was accepted and handle update rejection before presenting
  a teacher session as ready. This is a robustness recommendation; no live persona
  failure was reproduced. [Official OpenAI event reference](https://developers.openai.com/api/reference/resources/realtime/client-events).
- Separate calendar closure, feedback generation and mastery. Offline operation
  must not require a successful paid report before another week can open. Define
  study weekdays, pause/resume, timezone/DST behavior, and catch-up substitution
  within the daily time budget. These are P5-5/P5-6 decisions, not completed work.
- A default day-one speaking assignment is 25 minutes, while the shared Realtime
  screen caps a session at 20. Define the remaining practice time and distinguish
  learner speech from AI airtime before describing skill-time targets as achieved.
- Update plan status and test counts. P5-1 through P5-4 are committed; Today
  integration, reporting, and the planned navigation cleanup remain later tasks.
